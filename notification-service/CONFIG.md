# Notification Service Configuration

## Управление настройками

Все настройки сервиса уведомлений теперь управляются через веб-интерфейс:

**URL:** `http://localhost/notification-settings`

**Доступ:** Только для системных администраторов

## Настройки SMTP

Следующие параметры настраиваются через веб-интерфейс:

- **SMTP Сервер** - адрес SMTP сервера (например: smtp.gmail.com, 172.16.0.201)
- **SMTP Порт** - порт SMTP сервера (обычно 587 для TLS, 465 для SSL)
- **Пользователь SMTP** - имя пользователя для аутентификации
- **Пароль SMTP** - пароль или токен приложения
- **Отправитель (From)** - email адрес отправителя
- **Использовать TLS** - включение шифрования TLS
- **Требуется аутентификация** - включение аутентификации SMTP
- **Метод аутентификации** - PLAIN, LOGIN, CRAM-MD5

## Каналы доставки

Темп отправки, таймауты, повторы и очередь настраиваются **отдельно для каждого
канала** — в секции «Каналы доставки» на странице настроек или через API
(`GET /api/v1/channels`, `POST /api/v1/channels/{канал}`). Хранятся в таблице
`channel_configs`, по строке на канал.

У каждого канала своя очередь отправки и свой диспетчер, поэтому каналы не
влияют друг на друга: очередь почты не задерживает telegram, и наоборот.

### Действующие лимиты

| Канал | Лимит | Откуда |
|---|---|---|
| email | 1 сообщение раз в 4 с (15/мин) | администраторы почтового сервера разрешают 20/мин, взят запас |
| telegram | 30 сообщений/с на бота | Telegram Bot API |
| telegram | 1 сообщение/с в личный чат | Telegram Bot API |
| telegram | 20 сообщений/мин в группу | Telegram Bot API |

Повышать эти значения без согласования нельзя: превышение почтовой квоты — это
претензия от администраторов, превышение лимитов Telegram — 429 на весь бот
портала, включая подтверждение входа.

### Параметры канала

**Темп отправки**

- `min_interval_ms` — жёсткая пауза между сообщениями канала
- `rate_per_minute` — устойчивая скорость; `0` = без ограничения
- `burst` — сколько сообщений можно отправить подряд без паузы
- `quota_per_hour`, `quota_per_day` — суммарный потолок за окно; `0` = без квоты
**Приоритетная полоса**

- `priority_window_share_percent` — какую часть окна вправе занять приоритетная
  полоса; остаток зарезервирован за обычной очередью
- `service_priorities` — потолки приоритета отправителей для этого канала, JSON.
  Переопределяют общие из `SERVICE_PRIORITIES`; пусто = действуют общие

**Лимит на получателя**

- `per_recipient_per_minute`, `per_recipient_burst` — лимит на одного получателя
- `recipient_class_limits` — переопределения по классам получателей, JSON.
  Класс определяет транспорт канала; у telegram это `group` для групповых чатов
  (отрицательный `chat_id`): `{"group":{"per_minute":20,"burst":1}}`

**Таймауты**

- `connect_timeout_ms` — установка соединения
- `send_timeout_ms` — потолок на всю отправку одного сообщения

**Повторные попытки**

- `max_attempts` — попыток доставки
- `backoff_base_ms`, `backoff_max_ms` — экспоненциальная пауза и её потолок
- `respect_retry_after` — учитывать срок, названный провайдером в ответе 429
- `max_rate_limit_retries` — повторов при отказе по темпу. Считается отдельно от
  `max_attempts`: провайдер не отверг сообщение, а попросил подождать, и такой
  отказ не должен съедать попытки доставки

**Очередь канала**

- `max_concurrent` — сколько отправок канала идут одновременно
- `drain_batch_size` — сколько уведомлений диспетчер берёт из очереди за проход
- `max_inline_wait_ms` — ожидание из-за лимита канала, которое диспетчер
  выдерживает на месте; сверх него уведомление возвращается в очередь
- `max_inline_recipient_wait_ms` — то же для лимита получателя. Держится
  коротким: занятый получатель не должен задерживать остальных

**Прочее**

- `enabled` — выключенный канал не обрабатывает очередь (уведомления копятся)
- `extra` — параметры, специфичные для канала (JSON); читает только его транспорт

## Добавление нового канала

1. Реализовать интерфейс `Transport` (`transports.go`): отправка, разбор ошибок,
   ключ и класс получателя для лимитера.
2. Зарегистрировать транспорт в `buildTransports`.
3. Добавить заводской конфиг в `defaultChannelConfigs` (`channels.go`).

Очередь, диспетчер, лимитер, API конфигов и страница настроек подхватывают новый
канал сами — править их не нужно.

## Приоритетная полоса

При жёсткой квоте почты (15 писем в минуту) массовая рассылка на сотню адресов
занимает семь минут. Без приоритета письмо со сбросом пароля, попавшее в очередь
следом, ждало бы всю рассылку — пользователь стоит перед экраном и ждёт.

Очередь канала упорядочена по приоритету, затем по времени создания.

### Кто получает приоритет

Приоритет назначает **сам notification-service по отправителю**, а не запрос.
Потолок сервиса задаётся в `SERVICE_PRIORITIES`:

```
SERVICE_PRIORITIES=auth-service=100
```

Потолок — это и приоритет по умолчанию: вызывающему сервису **не нужно менять
свой код**, чтобы попасть в полосу.

### Потолки отдельно для канала

`SERVICE_PRIORITIES` задаёт потолки для всех каналов сразу. Настройка канала
`service_priorities` переопределяет их **для этого канала**:

```json
{"auth-service": 100, "monitoring-service": 50}
```

Цена задержки у каналов разная: подтверждение входа в telegram уходит мгновенно
и в полосе не нуждается, а то же письмо стоит в очереди почты минутами. Пример —
приоритет auth-service только на почте:

```bash
# приоритет на почте (очередь медленная)
curl -X POST http://notification-service/api/v1/channels/email   -H "X-API-Key: $KEY" -H "Content-Type: application/json"   -d '{"service_priorities": "{\"auth-service\":100}"}'

# на telegram полоса не нужна: канал и так быстрый
curl -X POST http://notification-service/api/v1/channels/telegram   -H "X-API-Key: $KEY" -H "Content-Type: application/json"   -d '{"service_priorities": "{\"auth-service\":0}"}'
```

Правила разрешения:

1. Есть ключ сервиса в `service_priorities` канала — берётся его значение.
   **Явный `0` выключает** приоритет отправителя на этом канале.
2. Ключа нет — действует общий потолок из `SERVICE_PRIORITIES`.
3. Нет и там — уведомление идёт в обычной очереди.

Пустое значение или `{}` означает «канал своих потолков не задаёт». Действующие
потолки печатаются в лог при старте, включая пер-канальные переопределения.

**Условие:** имя отправителя берётся из его персонального ключа в
`SERVICE_API_KEYS`. Сервис, приходящий с общим `INTERNAL_API_KEY`, определяется
как `internal-shared-key` — неотличим от остальных легаси-отправителей и
приоритета не получит. При старте сервис печатает предупреждение, если
приоритетный сервис не зарегистрирован своим ключом.

### Понижение для массовых рассылок

Необязательное поле `priority` в запросе принимается, только если оно **не выше**
потолка отправителя. Так `auth-service` опускает свои массовые рассылки (создание
аккаунтов при импорте из Excel) в обычную очередь, оставляя полосу за
подтверждением входа и сбросом пароля:

```json
{ "type": "email", "login": "ivanov", "subject": "...", "content": "...", "priority": 0 }
```

Сервис без приоритетной полосы поднять себя не может: значение выше потолка
срезается до потолка. Фактический приоритет возвращается в ответе на
`POST /api/v1/notifications`.

### Доля окна

Приоритет не вытесняет обычную очередь целиком. Настройка канала
`priority_window_share_percent` (по умолчанию 75) ограничивает долю окна,
доступную полосе; остаток зарезервирован за неприоритетными уведомлениями.

Доля считается от пропускной способности **своего** канала, поэтому у каждого
она своя и настраивается независимо:

| Канал | Окно | Приоритету | Обычной очереди |
|---|---|---|---|
| email | 15/мин | 11 | 4 |
| telegram | 1800/мин | 1350 | 450 |
Выбрав свою долю, полоса ждёт следующего окна, а остаток окна идёт массовой
рассылке — она продвигается всегда, пусть и медленно.

Цена: всплеск из одних приоритетных писем идёт 11/мин вместо 15/мин — четыре
места в окне остаются за обычной очередью, даже когда её нет. Значения `0` и
`100` выключают резерв, и приоритет занимает всё окно.

Резерв считается для каждого настроенного окна канала: минуты темпа,
`quota_per_hour`, `quota_per_day`.

## Очередь отправки

Очередь хранится в таблице `notifications`: диспетчер канала выбирает строки со
статусом `pending`, у которых наступил `next_attempt_at`.

- API-обработчик только создаёт строки и будит диспетчер нужного канала
- уведомление, упёршееся в лимит, откладывается через `next_attempt_at`, а не
  держит воркер занятым
- порядок выборки — `priority DESC, id ASC`
- приход нового уведомления прерывает текущий проход: на медленном канале порция
  идёт минутами, и приоритетное уведомление не должно её дожидаться
- принятые уведомления переживают рестарт сервиса; строки, застрявшие в статусе
  `sending`, возвращаются в очередь при старте

## Настройки обработки (легаси)

Поля `max_retry_attempts`, `batch_size`, `delay_between_batches_ms`,
`delay_between_messages_ms`, `telegram_delay_between_messages_ms` в общем конфиге
сохранены для старых клиентов API. На отправку они больше не влияют — темпом и
повторами управляют конфиги каналов. При первом создании строк каналов старые
значения задержек переносятся в `min_interval_ms` соответствующего канала.

## Тестирование

На странице настроек есть функция отправки тестового письма для проверки корректности конфигурации.

## Fallback настройки

В случае недоступности notification-service, auth-service использует fallback настройки из файла `.env`. Эти настройки должны быть синхронизированы с основными настройками.

## API

Для программного управления настройками доступно API:

- `GET /api/v1/config` - получение текущих настроек
- `POST /api/v1/config` - обновление настроек
- `GET /api/v1/channels` - конфиги каналов вместе с состоянием их очередей
- `POST /api/v1/channels/{канал}` - частичное обновление конфига канала
- `POST /api/v1/notifications` - отправка уведомления

## База данных

Общие настройки хранятся в таблице `notification_configs`, конфиги каналов — в
`channel_configs` (по строке на канал), очередь отправки — в `notifications`.
База данных PostgreSQL notification-service.
