# Страницы ошибок шлюза

Исходники стилизованных страниц ошибок. Готовые файлы лежат в
`../html/errors/` и **правятся только генератором**.

Покрыт весь список кодов, которые может отдать шлюз или сервис, включая
`403` и редкие вроде `418 I'm a teapot`. Не покрыт только `401` — он уводит
на форму входа.

## Что где

| Файл | Роль |
|---|---|
| `codes.py` | каталог: код → заголовок, текст, подсказка, иллюстрация |
| `errors.css` | стили; палитра скопирована из портала (см. ниже, почему не подключена) |
| `generate.py` | сборка страниц, `errors-pages.inc` и `errors-preview.inc` |
| `tests/test_error_pages.py` | проверки; сети и докера не требуют |
| `../conf/errors.inc` | обвязка nginx: перехват, раздача, заголовки — пишется руками |

## Как поменять текст ошибки

```bash
# 1. правка в codes.py
# 2. пересборка
python generate.py
# 3. проверка
python -m pytest tests -q
# 4. применение без пересборки образа (каталог смонтирован в контейнер)
docker exec gateway-nginx-1 nginx -t && docker kill -s HUP gateway-nginx-1
```

Новый код добавляется одной записью в `CODES`: генератор сам создаст страницу,
строку `error_page` и location предпросмотра.

## Как посмотреть все страницы

`https://analytics.gh.uz/errors-preview/` — витрина, доступна только
администратору. Ссылки возвращают настоящий статус-код, а не имитацию:
`location = /errors-preview/418 { return 418; }`, дальше отрабатывает обычный
`error_page`.

Открывать `html/errors/*.html` файлом в браузере смысла мало — без nginx не
выполняется SSI, поэтому тема и технические поля останутся пустыми.

## Три решения, которые выглядят странно, но приняты осознанно

**Палитра скопирована, а не подключена.** Страница ошибки нужна ровно тогда,
когда лежит `auth-service`, — а вместе с ним недоступен и
`/static/css/styles.css`. Поэтому `errors.css` отдаёт сам nginx, без внешних
загрузок вообще: прод в изолированной сети, CDN недоступен. Цена — при смене
фирменных цветов в `auth-service/static/css/styles.css` правится и этот файл.

**Страница на каждый код, а не одна с подстановкой.** Внутри обработки
`error_page` переменная `$status` уже равна коду обрабатываемой страницы,
а не исходной ошибки, поэтому «одна страница на все коды» пришлось бы
собирать через named location на каждый код. Отдельный файл на код проще
и читается без комментариев.

**Класс темы подставляется внутрь значения атрибута.** Одинарные кавычки и
`class='<!--# if ... -->dark-theme<!--# endif -->'` вместо подстановки самого
атрибута: при выключенном SSI страница получит бессмысленный класс, который
браузер проигнорирует, вместо куска разметки видимым текстом.

## Тема

Та же, что выбрана на портале. Источник — cookie `gh_theme`, которую пишет
`auth-service/static/js/theme-switcher.js`; порядок тот же, что у портала:
cookie → `localStorage` → системная тема.

Читают её **два независимых пути**, и это не дублирование:

| Путь | Зачем |
|---|---|
| SSI подставляет класс в `<html>` | тема стоит до первой отрисовки, без вспышки светлым; работает без JS |
| инлайновый скрипт | страница попадает в тему, даже если SSI не отработал — например, конфиг в контейнере устарел |

Скрипт сверяет класс **точно** — `=== 'dark-theme'`, а не «класс непустой».
При выключенном SSI на `<html>` остаётся заглушка `dark-themelight-theme`:
она непустая, и грубая проверка приняла бы её за уже применённую тему.

## Правило про кавычки в атрибутах

**Директива SSI внутри атрибута — только на одинарных кавычках.**

Директива несёт двойные кавычки внутри себя (`<!--# echo var="…" -->`).
В атрибуте на двойных кавычках браузер, которому SSI не обработали, обрывает
значение на первой внутренней кавычке и вываливает хвост тега видимым текстом
поверх страницы. На одинарных худшее, что выйдет, — бессмысленное значение
атрибута, которого никто не заметит.

Касается `class` на `<html>` и `href` ссылки на поддержку. Проверка — тест
`test_ssi_в_атрибутах_только_на_одинарных_кавычках`.

## Ссылка на поддержку

Берётся из переменной окружения `SUPPORT_TELEGRAM` (логин без `@`).
nginx окружение в конфиге не читает, поэтому цепочка такая:

```
.env → docker-compose.yaml → окружение контейнера
     → docker-entrypoint.sh → conf.d/errors-contact.inc
     → set $gw_support_telegram → SSI на странице
```

Значение чистится до `[A-Za-z0-9_]`: подставлять сырую переменную окружения
в конфиг нельзя — кавычка или перевод строки в ней не дадут шлюзу подняться.
Пусто или не задано — блок со ссылкой не выводится вовсе.

Смена значения требует пересоздания контейнера: `restart` не перечитывает
`env_file`.

```bash
docker compose up -d --force-recreate nginx
```

## Фон с частицами

Тот же `particles.js`, что на остальных страницах портала, из
`/_shared/js/particles.min.js` — файл отдаёт сам nginx, поэтому фон жив и при
мёртвом auth-service. Цвет берётся из CSS-переменной `--err-particles`, своей
на каждую тему.

Инициализация молча пропускается, если скрипта нет или у пользователя включён
`prefers-reduced-motion` — анимация на весь экран не должна быть обязательной.
На экранах уже 700 px частиц вдвое меньше: на телефоне сотня шестиугольников
греет батарею и заметно подтормаживает.

## Что показывает страница и откуда берёт

| Поле | Источник |
|---|---|
| раздел | `$gw_service_key` из конфига сервиса, иначе первый сегмент пути (`map $gw_path_service`) |
| ответ раздела | `$upstream_status` |
| код и подробности ошибки | заголовки ответа сервиса `X-Error-Code`, `X-Error-Detail` |
| узел | `$upstream_addr` |
| запрос, время, идентификатор | `$request_method`, `$request_uri`, `$time_iso8601`, `$request_id` |
| ссылка на поддержку | `$gw_support_telegram` из переменной окружения `SUPPORT_TELEGRAM` |

**Тело ответа сервиса на страницу не попадает и попасть не может**:
`proxy_intercept_errors` заставляет nginx выбросить его, а разбирать JSON
nginx не умеет. Сервису, которому есть что сказать пользователю, остаётся
заголовок `X-Error-Detail` — он и выводится в подробностях.

## Где включён перехват и почему не везде

`proxy_intercept_errors on` объявлен на весь server-блок: все страницы ошибок
на портале — эти. Снят он только там, где не-2xx является содержимым или
служебным сигналом: `/login` (отдаёт `401` вместе с «неверный пароль»),
`/forgot-password` и `/reset-password` (`500` вместе со страницей результата),
`/api/`, ассеты, подзапросы `auth_request`, вебсокеты Dozzle, а у сервисов —
`<prefix>/static/` и `<prefix>/health`. Полный список с обоснованием —
в шапке `../conf/errors.inc`.

## Правило, которое нельзя нарушать

**`error_page` перехватываемого кода ведёт на файл, а не на редирект.**

Внутренний редирект на статику терминален. Редирект же уходит клиенту, и если
его цель отдаёт тот же код — получается цикл. Ровно так было с
`error_page 403 = 302 /access-denied`: страница отказа сама отвечает `403`,
шлюз снова слал `302` на неё же, браузер крутился до отказа.

Поэтому бюджет: **браузер видит не больше одного редиректа на ошибку**, и
остался он только у `401` на `/login` — это не отказ, а «представьтесь».
Всё остальное, включая `403`, рисуется прямо на исходном URL.

SSI-директива `echo` по умолчанию экранирует значение (`encoding="entity"`).
`$request_uri` и заголовки сервиса приходят снаружи, поэтому
**`encoding="none"` в этих страницах не использовать** — это прямая XSS.
Проверка стоит в тестах.
